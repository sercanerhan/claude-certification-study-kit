## Core idea
The model chooses a tool mainly by reading its name and description. A one-line description such as "Retrieves order details" gives it nothing to separate two similar tools, so it misroutes. An architect treats each description as a contract. It says what the tool does, what input it expects, what it returns, and when to use it instead of its neighbour.

## What the exam tests
- Descriptions are the **primary** selection signal. Thin descriptions cause unreliable choices between look-alike tools.
- A good description covers input formats, example queries, edge cases and boundaries ("use this for X, not for Y; for Y use `other_tool`").
- Overlapping names and descriptions cause misrouting (`analyze_content` vs `analyze_document`). Fix it by **renaming** (`extract_web_results`) and rewriting the description so the purposes no longer overlap.
- Split a generic tool into purpose-specific tools with clear input/output contracts. For example, `analyze_document` becomes `extract_data_points`, `summarize_content` and `verify_claim_against_source`.
- Keyword-sensitive system-prompt lines ("whenever the user says *account*, call get_customer") can override good descriptions. Review the system prompt as well as the tools.

## Exam traps
- **Trap:** add few-shot routing examples or a keyword router first → **Instead:** fix the descriptions first. They are the root cause, and fixing them is cheap and high-leverage.
- **Trap:** merge two confusable tools into one `lookup_entity` as the first step → **Instead:** merging is a valid redesign, but it costs more than a "first step" justifies. Clarify the descriptions first.
- **Trap:** blame the model when one word in the user message always triggers the wrong tool → **Instead:** look for a keyword-triggered instruction in the system prompt.
- **Trap:** rely on the tool *name* alone to communicate purpose → **Instead:** the name helps, but the description carries the boundaries and the formats.

## Example
```json
{"name": "search_code_index",
 "description": "Semantic search over the pre-built code index for symbols, call sites and cross-repo references. Input: a symbol or natural-language question (e.g. 'who calls chargeCard'). Returns file, line, enclosing function. Use this instead of plain text search when you need callers across repos or renamed imports. Does NOT search non-code files; use Grep for logs/config."}
```

## Remember
- Description = the model's routing table. Write 3–4+ sentences for each tool.
- Say when **not** to use the tool, and name the alternative.
- Rename and split tools to remove overlap. Don't paper over it with prompts.
- Audit the system prompt for keyword triggers.
- Docs note: the current tool-use docs also suggest *consolidating* related actions into one tool with an `action` parameter. The exam's "split generic tools" skill aims at the same goal: no functional overlap.
