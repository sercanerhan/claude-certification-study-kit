## Core idea
The Message Batches API runs many independent Messages requests asynchronously at **50% of the price**. In exchange, processing can take **up to 24 hours** and there is **no latency SLA**. Use it for latency-tolerant work (overnight reports, weekly audits, nightly test generation, bulk extraction). Never use it for anything that blocks a person, such as a pre-merge check. Each request returns **one response**: your code cannot run a tool partway through a request and feed the result back.

## What the exam tests
- Matching API to latency: synchronous calls for blocking pre-merge checks, batch for overnight/weekly jobs.
- **No multi-turn tool calling inside a request.** Iterative "Claude asks for a file, you return it" flows do not fit a batch. Put all the context into the request up front, or run the loop synchronously.
- **`custom_id`** links each result to its request. Results can arrive in **any order**.
- **Failure handling:** read results by `custom_id` and resubmit **only** the `errored`/`expired` ones, changed where needed (for example, split documents that were too long for the context window).
- **SLA math:** worst case = wait until the next submission + 24 h. For a 30 h SLA, submit every **4 h** (4 + 24 = 28 h, which leaves a buffer).
- Refine the prompt on a **sample set** first to raise the first-pass success rate before batching large volumes.

## Exam traps
- **Trap:** batch the pre-merge check too, since most batches finish within an hour → **Instead:** keep it synchronous. "Usually fast" is not a guarantee.
- **Trap:** batch with a timeout fallback to real-time → **Instead:** split the workloads by latency need. The fallback adds complexity for nothing.
- **Trap:** resubmit the whole batch after partial failure → **Instead:** resubmit only the failed `custom_id`s. Resubmitting everything doubles cost.
- **Trap:** say "batch doesn't support tools" → **Instead:** note that tool *definitions* are allowed. What is impossible is running a tool and returning its result within the same request.

## Example
```text
SLA = 30 h after a document arrives, batch worst case = 24 h
submit interval ≤ 30 − 24 = 6 h  → choose 4 h for buffer (4 + 24 = 28 h)
results: custom_id "inv-2026-0042" → errored (prompt too long)
         → resubmit as "inv-2026-0042-p1", "inv-2026-0042-p2" (chunked)
```

## Remember
- 50% cheaper, up to 24 h, no SLA.
- Blocking work stays synchronous. Overnight or weekly work goes to batch.
- One request = one response. No tool round trip mid-request.
- `custom_id` (1–64 chars, `[A-Za-z0-9_-]`) maps results, because order is not guaranteed.
- Docs: errored and expired requests are not billed. A batch holds at most 100,000 requests or 256 MB.
