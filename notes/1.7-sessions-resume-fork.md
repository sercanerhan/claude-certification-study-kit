## Core idea
A session is the stored conversation history: prompts, tool calls, results and reasoning. **Resuming** continues a specific earlier session with all of that context. **Forking** copies a session's history into a new, independent session, so you can try another direction while the original stays untouched. The architect's judgment is knowing when the old context is still trustworthy. If the earlier tool results are **stale**, a fresh session with an injected structured summary is more reliable than resuming.

## What the exam tests
- Named resumption: `--resume <session-name>` continues a specific prior conversation across work sessions.
- `fork_session` creates independent branches from a shared analysis baseline, for example to compare two refactoring or testing strategies.
- After code or data changes, **tell the resumed agent what changed** (specific files) so it re-analyses only those, not everything.
- Choose **resume** when the prior context is mostly valid. Choose **fresh + summary** when the prior tool results are stale.

## Exam traps
- **Trap:** resume and assume the agent will notice that files changed → **Instead:** say exactly which files changed. Stale results look authoritative.
- **Trap:** resume a long session whose tool results are outdated → **Instead:** start fresh and inject a structured summary of the key facts and decisions.
- **Trap:** compare two approaches by asking for both in the same session → **Instead:** fork, so the second branch isn't influenced by the first.
- **Trap:** re-run the whole analysis twice for two alternatives → **Instead:** fork from the shared baseline. It's cheaper and the baseline is identical.
- **Trap:** fork to "protect" yourself from stale data → **Instead:** a fork copies the same stale history.

## Example
```bash
claude -n "refund-flow-audit"                          # name the session
claude --resume refund-flow-audit "src/refund.ts changed: re-check only that file"
claude --resume refund-flow-audit --fork-session "Try strategy B: contract tests"
```

## Remember
- `--resume <name|id>` continues. `fork_session` / `--fork-session` branches with a new session ID and leaves the original unchanged.
- Forks branch the conversation, not the filesystem. Edits a fork makes are real.
- Mostly valid context → resume and name the changed files. Stale context → fresh session plus a summary.
- Get the session ID from the result message (`session_id`) to resume programmatically.
