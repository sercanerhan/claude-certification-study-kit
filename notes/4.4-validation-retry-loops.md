## Core idea
Schema-valid output can still be wrong, so validate it in code: check sums, cross-field rules and plausible ranges. When validation fails, **retry with error feedback**: send the original document, the failed extraction and the specific validation errors so the model can correct itself. Retries fix format and structural mistakes. They cannot produce information that is not in the input. Recognizing which failures can never succeed on retry is a core skill.

## What the exam tests
- A follow-up request should contain three things: **original document + failed extraction + specific errors**. A bare "try again" is not enough.
- Retry **works** for format mismatches, misplaced fields and arithmetic slips. It **does not work** when the data is absent or lives in an external document that was not provided.
- Syntax errors are removed by tool use. Semantic errors (totals do not match, wrong field) need validation logic.
- Self-correction fields: extract `stated_total` **and** `calculated_total`, and set `conflict_detected` when the source contradicts itself.
- Feedback loops: add a `detected_pattern` field to each finding so dismissals can be grouped by code construct, which shows which patterns cause false positives.

## Exam traps
- **Trap:** retry up to N times with the same prompt, or with higher temperature → **Instead:** send the specific error. Without feedback the model repeats the mistake.
- **Trap:** keep retrying when the value is not in the document → **Instead:** return null and route the item to a human or fetch the missing source. Retries burn cost and push the model toward fabrication.
- **Trap:** let the model silently "fix" totals so they match → **Instead:** extract both values and flag the conflict. The discrepancy is itself information downstream systems need.
- **Trap:** believe strict schemas already guarantee correct values → **Instead:** add semantic checks in code.
- **Trap:** analyze developer dismissals by reading comments by hand → **Instead:** use a structured `detected_pattern` field so the analysis can be done systematically.

## Example
```text
Retry prompt (2nd attempt):
<document>{{original}}</document>
<previous_extraction>{{json}}</previous_extraction>
<validation_errors>
- line_items sum to 1,240.00 but total = 1,420.00; re-read the items table
- invoice_date "03/04/24" is not ISO 8601; use YYYY-MM-DD
</validation_errors>
Correct only the fields above. If a value is not present in the document, return null.
```

## Remember
- Retry = document + failed output + specific errors.
- Retries fix format/structure, never absent information.
- `calculated_total` vs `stated_total` + `conflict_detected` surface source inconsistencies.
- `detected_pattern` turns dismissals into analyzable false-positive data.
- Docs: SDK helpers such as Pydantic `messages.parse()` validate locally. Constraints like `minimum`/`maximum` are not enforced by the schema grammar.
