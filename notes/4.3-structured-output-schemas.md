title: Structured output with tool use & JSON schemas

## Core idea
To get machine-readable output reliably, define an extraction **tool** whose `input_schema` is your JSON schema and read the result from the `tool_use` block. That removes JSON syntax errors. It does **not** make values correct. Most of the exam's points come from schema design: decide which fields are required and which are nullable, and give categories an escape value such as `"other"` or `"unclear"`, so the model is never pushed into making something up.

## What the exam tests
- `tool_choice`: `"auto"` means the model may answer in text instead. `"any"` means it must call *some* tool (use this with several schemas when the document type is unknown). `{"type":"tool","name":"extract_metadata"}` means it must call *that* tool (use this to force a first step before enrichment). `"none"` means no tools.
- A strict schema blocks syntax errors, but semantic errors still get through: line items that do not sum to the total, or a value in the wrong field.
- **Nullable/optional fields** for information that may be missing. If a field is required and non-null, the model fabricates a value to fill it.
- **Enum + `"other"` + detail string** for categories that grow over time. Add `"unclear"` for ambiguous cases.
- Put **format normalization rules** in the prompt (ISO dates, currency codes, units) alongside the schema.

## Exam traps
- **Trap:** keep a field required and add "do not invent values" to the prompt → **Instead:** make the field nullable. The schema itself is what forces the fabrication.
- **Trap:** keep extending a closed enum to cover each new category → **Instead:** add `"other"` plus a `*_detail` string. A closed list forces wrong buckets.
- **Trap:** force one named tool when the document type is unknown → **Instead:** use `"any"`. Forcing a single schema fits it to the wrong document type.
- **Trap:** assume schema compliance means correct data → **Instead:** add semantic validation in code (task 4.4).

## Example
```json
{"name":"extract_invoice","input_schema":{"type":"object","properties":{
  "invoice_number":{"type":"string"},
  "po_number":{"type":["string","null"],"description":"null if not printed on the invoice"},
  "doc_type":{"type":"string","enum":["invoice","credit_note","proforma","other","unclear"]},
  "doc_type_detail":{"type":["string","null"],"description":"required when doc_type is other/unclear"}},
  "required":["invoice_number","po_number","doc_type","doc_type_detail"]}}
```
A field can be **required and nullable** at the same time: the key must be present, and `null` is an allowed value.

## Remember
- Tool use + schema removes syntax errors, not wrong values.
- `any` for unknown document types. A forced named tool for a mandatory first step.
- Nullable fields prevent fabrication.
- Use `other` + detail, and `unclear`, for categories.
- Docs today: `strict: true` and `output_config.format` ("structured outputs"). The newest models reject forced `any`/`tool` choice. For the exam, use the guide's `tool_choice` terms.
