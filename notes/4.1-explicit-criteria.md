title: Explicit criteria for precision
---
## Core idea
Vague instructions such as "check that comments are accurate" or "be conservative" leave the model to guess where the line is, so it guesses differently every run. Precision comes from **categorical criteria**: say exactly what to report, what to skip, and how to grade severity, with a concrete example for each level. False positives are an architecture problem as well as a quality problem. One noisy category teaches developers to ignore every finding, including the accurate ones.

## What the exam tests
- Replacing vague wording with explicit report/skip rules (report: bugs, security, behavior contradicting comments; skip: minor style, local conventions).
- Knowing that "only report high-confidence findings" does **not** raise precision. The model's confidence is not a calibrated filter.
- Defining severity levels with concrete code examples per level so the same issue gets the same rating in every PR.
- Restoring trust by **temporarily disabling** high false-positive categories while you fix their prompts, and keeping the high-precision ones.

## Exam traps
- **Trap:** add "be conservative" or "only flag issues you are sure about" → **Instead:** write explicit categorical criteria. Confidence-based wording barely changes precision.
- **Trap:** keep every category on and show confidence scores so developers can decide → **Instead:** switch off the noisy categories now. Developers who already distrust the tool will not read the scores.
- **Trap:** apply one uniform strictness reduction to all categories → **Instead:** treat categories separately. Security at 8% FP must not lose recall because style is at 50%.
- **Trap:** fix inconsistent severity by asking the model to "be consistent" → **Instead:** give a definition plus a code example for each level.
- **Trap:** filter TODO/FIXME comments out with a regex → **Instead:** state the criterion ("flag a comment only when its claimed behavior contradicts the code"). A regex treats the symptom and misses the real misleading comments.

## Example
```text
Report a comment ONLY if:
  1. It describes behavior the code no longer implements, or
  2. It names a function/parameter that does not exist.
Do NOT report: TODO/FIXME markers, terse but correct descriptions, wording style.
Severity:
  critical: user-facing failure    e.g. null deref in checkout path
  high:     security exposure      e.g. SQL built from request params
  medium:   wrong result, no crash e.g. off-by-one in pagination
  low:      maintainability        e.g. duplicated helper
```

## Remember
- Explicit categories beat vague cautions every time.
- "High-confidence only" is not a precision control.
- Severity needs definitions **and** code examples per level.
- Disable noisy categories temporarily, fix their prompts, then re-enable.
- High false positives in one category erode trust in all of them.
