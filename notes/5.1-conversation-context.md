title: Preserving critical information in long contexts
---
## Core idea
Long conversations and multi-agent pipelines lose information in predictable ways. Summaries blur exact numbers, details in the middle of long inputs get overlooked, and verbose tool results crowd out what matters. The fix is to manage the context deliberately: keep transactional facts outside the summarised history, trim tool output before it piles up, put the key findings where the model reads most reliably, and have upstream agents return structured data rather than raw text.

## What the exam tests
- Progressive summarisation turns amounts, percentages, dates and customer expectations into vague phrases ("a discount was discussed").
- The **lost-in-the-middle** effect: the beginning and end of a long input are processed reliably, the middle less so.
- Tool results consume tokens out of proportion to their relevance (40+ fields per order when 5 matter).
- Send the full conversation history with each API request to keep the conversation coherent.
- Persist a **case facts** block (amounts, dates, order IDs, statuses) in every prompt, outside the summarised history. For multi-issue sessions, keep a separate structured issue layer.
- Trim tool outputs to the relevant fields. Put a key-findings summary first and use explicit section headers.
- Subagents return structured outputs with metadata (dates, sources, method), and upstream agents send key facts, citations and relevance scores rather than verbose reasoning when downstream budgets are tight.

## Exam traps
- **Trap:** improve the summarisation prompt to "keep all numbers" → **Instead:** extract the facts into a persistent block. Repeated compression is still lossy.
- **Trap:** raise the summarisation threshold → **Instead:** that only delays the loss.
- **Trap:** synthesis misses mid-input findings, so rotate the input order → **Instead:** put a key-findings summary up front and add section headers.
- **Trap:** 155K tokens of upstream output, so add a summariser agent → **Instead:** change the upstream agents to emit structured facts.
- **Trap:** keep full order records "just in case" → **Instead:** trim them to the fields the task needs.

## Example
```text
<case_facts>   (re-sent every turn, never summarised)
customer_id: C-4471 | order: #88213 | amount_disputed: $129.00
promised: 15% loyalty discount on next order (turn 4)
status: refund pending approval
</case_facts>
<summary_of_earlier_turns> ... </summary_of_earlier_turns>
```

## Remember
- Exact facts go in a persistent block, not the summary.
- The middle is the weak spot: summary first, then headers.
- Trim tool output at the source.
- Upstream sends structured facts, not page dumps or reasoning chains.
