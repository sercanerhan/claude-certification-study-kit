## Core idea
Some workflow steps must happen in a fixed order. For example, verify identity before touching money. A prompt can *ask* for that order, but prompt compliance is probabilistic, so a small share of conversations will skip the step. When the consequences are serious, enforce the order in **code**: hooks or prerequisite gates that block downstream tool calls until the required step has succeeded. When work moves to a human mid-process, pass a **structured handoff** that lets them act without the transcript.

## What the exam tests
- **Programmatic enforcement** (hooks, prerequisite gates) vs **prompt-based guidance** for ordering.
- Prompts have a **non-zero failure rate**. Use deterministic enforcement when compliance must be guaranteed (identity before financial operations).
- Block `process_refund` (and order operations) until `get_customer` has returned a **verified customer ID**.
- Decompose **multi-concern requests** into distinct items, investigate them in parallel with **shared context**, then synthesise one resolution.
- **Structured handoff** when escalating: customer ID, root cause, refund amount, actions taken, recommended action. The human can't see the transcript.

## Exam traps
- **Trap:** the agent skips verification 12% of the time, so make the prompt say MANDATORY → **Instead:** add a programmatic prerequisite. Stronger wording is still probabilistic.
- **Trap:** add few-shot examples of calling `get_customer` first → **Instead:** helpful, but not a guarantee when money is at stake.
- **Trap:** a routing classifier that enables only some tools per request → **Instead:** that controls which tools are *available*, not the *order* they run in.
- **Trap:** escalate with "customer needs help" or a raw transcript dump → **Instead:** a structured summary with root cause and a recommended next step.
- **Trap:** handle a three-issue message strictly one issue at a time, re-fetching the customer each time → **Instead:** fetch the customer once, then investigate the issues in parallel.

## Example
```python
verified = {}  # session_id -> customer_id
async def gate(inp, tool_use_id, ctx):
    if inp["tool_name"] in ("mcp__support__process_refund", "mcp__support__lookup_order") \
       and inp["session_id"] not in verified:
        return {"hookSpecificOutput": {"hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason": "Call get_customer and verify the customer first."}}
    return {}
```
The handoff schema for `escalate_to_human` includes `customer_id`, `issue_summary`, `root_cause`, `amount`, `actions_taken` and `recommended_action`.

## Remember
- Prompts guide, code guarantees.
- When there are financial or identity consequences, use a prerequisite gate.
- An available tool is not the same as an ordered tool.
- Multi-issue requests: decompose, use shared context, investigate in parallel, then give one answer.
- The handoff must be complete without the transcript.
