## Core idea
When Claude's output keeps missing the target, don't just rewrite the request in more words. Give it something **unambiguous to aim at**:
- concrete input/output examples;
- a test suite whose failures you feed back;
- an interview, where Claude asks you questions before it builds.

Then decide whether to send all the remaining problems in one message or fix them one by one.

## What the exam tests
- 2–3 concrete input/output examples are the most effective fix when prose descriptions are interpreted inconsistently.
- Test-driven iteration: write tests first (expected behaviour, edge cases, performance), then iterate by sharing the specific failures.
- The interview pattern: have Claude ask clarifying questions to surface considerations you hadn't anticipated (cache invalidation, failure modes) before it implements in an unfamiliar domain.
- To fix an edge case, give a specific test case with example input and expected output (e.g. null values in a migration script).
- **Interacting** issues go in one detailed message, because fixing one affects the others. **Independent** issues can be fixed one at a time.

## Exam traps
- **Trap:** rewrite the requirements with more technical precision → **Instead:** show 2–3 input→output pairs. Examples beat prose for transformations.
- **Trap:** ask Claude to explain its understanding again → **Instead:** that diagnoses the problem but doesn't anchor the output. Examples or tests do.
- **Trap:** fix three interacting issues one per message → **Instead:** send one combined message, or each fix can undo the others.
- **Trap:** start implementing a caching layer in an unfamiliar domain straight away → **Instead:** run the interview pattern first.

## Example
```
Input:  {"ts": 1714003200, "user": {"id": 7}}
Output: {"timestamp": "2024-04-25T00:00:00Z", "userId": 7}
Input:  {"ts": null, "user": null}
Output: {"timestamp": null, "userId": null}
```

## Remember
- Examples > adjectives for transformations.
- Tests first, then iterate on the failures.
- Interview first in unfamiliar domains.
- Interacting issues → one message. Independent issues → sequential fixes.
